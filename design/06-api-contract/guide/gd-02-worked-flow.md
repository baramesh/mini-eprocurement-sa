# ตัวอย่าง flow: ผู้ขอซื้อสร้างและส่งใบขอซื้อ

flow นี้เริ่มที่หน้าแบบฟอร์มใบขอซื้อ (SCR-02) ผู้ขอซื้อกรอกฟอร์ม กดบันทึกร่าง แก้ไข แล้วกดส่งอนุมัติ เรียก operation สามตัว คือ `createPurchaseRequest`, `updatePurchaseRequest` และ `submitPurchaseRequest` ตารางข้างล่างบอกว่านักพัฒนาแต่ละฝั่งอ่านอะไร ตรงไหน ตามลำดับ

<!-- table: ฝั่งหน้าบ้าน อ่านตามลำดับนี้ -->
| ลำดับ | ต้องการรู้ | อ่านที่ | ได้อะไรไปเขียน |
|---|---|---|---|
| 1 | หน้านี้ใครเข้าได้ ไปไหนต่อ | เล่มการออกแบบ UX/UI: รายละเอียดหน้าจอ SCR-02 และผังการนำทาง | เส้นทาง `/purchase-requests/new` และ `/purchase-requests/{prId}` บทบาทที่เข้าได้ หน้าถัดไปหลังส่ง (กลับรายการ) |
| 2 | หน้าตาและฟิลด์ | wireframe WF-02 | ฟิลด์ หัวข้อ เหตุผล วันที่ต้องการใช้ ตารางรายการ วงเงินรวม ปุ่มสามปุ่ม และกติกาของแต่ละฟิลด์ |
| 3 | กฎที่ใช้ทุกหน้า | กฎกลางของหน้าจอ | วันที่แสดงเป็น พ.ศ. เงินมีทศนิยม 2 ตำแหน่งชิดขวา สถานะต้องมีข้อความ ปุ่มที่เรียก API ปิดระหว่างรอและสร้าง `Idempotency-Key` ใหม่ต่อการกระทำ |
| 4 | กดปุ่มแต่ละปุ่มแล้วเกิดอะไร | พฤติกรรมของหน้า SCR-02 (UIX-02): ตารางเหตุการณ์ | บันทึกร่างครั้งแรกเรียก create ครั้งต่อไปเรียก update พร้อม `If-Match` ส่งอนุมัติถ้ามีการแก้ค้างให้ update ก่อนแล้ว submit |
| 5 | ส่งและอ่านฟิลด์ใดของ API | UIX-02: ตารางผูกหน้าจอกับ API | รายการ `sends` และ `reads` ของแต่ละปุ่ม (ตัวตรวจเทียบกับสัญญาให้แล้ว) |
| 6 | รูปแบบ request และ response จริง | เล่มข้อกำหนด REST API: operation ทั้งสาม (ตารางข้อมูลทั่วไป request body response ตัวอย่าง) และไฟล์ `api/examples/createPurchaseRequest.request.json` กับ `...response.201.json` | ชนิดข้อมูล ข้อจำกัด รหัสผลลัพธ์ทุกแบบ ตัวอย่างไว้ทำ mock |
| 7 | header ที่ต้องส่ง | หลักการทั่วไปของ API: การยืนยันตัวตน (CNV-03) การเรียกซ้ำ (CNV-05) การแก้ไขซ้อน (CNV-06) | `Authorization`, `Idempotency-Key` (คำสั่งเปลี่ยนสถานะ), `If-Match` (เฉพาะ update), claim `sub` ไว้รู้ว่าผู้ใช้คือใคร |
| 8 | ผิดพลาดแล้วแสดงอะไร | UIX-02: ตารางสถานะ และหน้ารหัสข้อผิดพลาด | 422 แสดงข้อความใต้ฟิลด์ใน `details[]`, 409 `ERR-CONC-001` ให้โหลดข้อมูลล่าสุด, 409 `ERR-STATE-001` แสดงสถานะล่าสุด, 401 ไปยืนยันตัวตนใหม่ |
| 9 | พิสูจน์ว่าถูก | เกณฑ์ตรวจรับ AC-01-03 AC-01-04 และการทดสอบ `tests/api-trial/e2e/flow.spec.ts` ขั้นต้น | กรณีทดสอบและตัวอย่างหน้าจอที่ทำงานตามเอกสารนี้ (`reference/web`) |

<!-- table: ฝั่งหลังบ้าน อ่านตามลำดับนี้ -->
| ลำดับ | ต้องการรู้ | อ่านที่ | ได้อะไรไปเขียน |
|---|---|---|---|
| 1 | โค้ดวางอย่างไร รันอย่างไร | สถาปัตยกรรม: โครงสร้างโค้ด (DEV-03 การสร้างและรัน) | สร้างชุดรันบนเครื่องด้วย `docker compose` ข้อจำกัดของ stack |
| 2 | ทุกคำขอต้องผ่านอะไรก่อน | สถาปัตยกรรม: แนวคิดที่ใช้ร่วม (การตรวจสิทธิ์ CPT-01, idempotency CPT-02, เลขที่เอกสาร CPT-04) และ runtime view V-06 | ลำดับตรวจ token ผู้ใช้ บทบาท ขอบเขตข้อมูล คีย์ idempotency เป็น middleware ร่วม |
| 3 | operation ทำงานภายในอย่างไร | สถาปัตยกรรม: runtime view ตามช่อง "Runtime view" ของ operation: V-08 (create กับ update) และ V-03 (submit) | ลำดับขั้นพร้อมรหัสผิดพลาดของแต่ละขั้น เช่น ตรวจรูปแบบก่อน ออกเลขที่ก่อนเริ่มธุรกรรม ตรวจ `If-Match` แล้วตรวจสถานะ `DRAFT` สร้างสายอนุมัติตามวงเงิน |
| 4 | request และ response เป็นอย่างไร | เล่มข้อกำหนด REST API: operation ทั้งสาม | schema ที่ต้องตรวจ บทบาทที่เรียกได้ รหัสผลลัพธ์ทุกแบบ |
| 5 | เขียนตารางไหน ค่ามาจากไหน | เล่มข้อกำหนด REST API: ตาราง "ข้อมูลที่บันทึก" ของแต่ละ operation และคอลัมน์ "ที่มา" ของ response | ค่าทุกคอลัมน์ของ `purchase_request`, `pr_item`, `approval`, `audit_log` ทั้งที่มาจาก request, token, เวลา, เลขที่เอกสาร หรือการคำนวณ |
| 6 | ตารางและคอลัมน์มีกฎอย่างไร | เล่มการออกแบบฐานข้อมูล: พจนานุกรมข้อมูลของตารางทั้งสี่ และ `sql/schema.sql` (รวม `usp_next_doc_no`) | ชนิดข้อมูล ข้อจำกัด ดัชนี `row_version` |
| 7 | กฎธุรกิจ | กฎ BR-03 (สายอนุมัติตามวงเงิน) BR-12 (ส่งแล้วแก้ไม่ได้) และหลักการทั่วไป: รูปแบบข้อมูล (CNV-02) | วงเงิน 20,000.00 ได้ 1 ขั้น 20,000.01 ได้ 2 ขั้น ปัดเศษครึ่งขึ้นทีละบรรทัด |
| 8 | ผลลัพธ์ที่ถูกต้อง | เกณฑ์ตรวจรับ AC-01-01 AC-01-04 AC-03-02 AC-03-05 AC-03-06 และ `tests/api-trial/specs/acceptance.spec.ts` | ชุดทดสอบที่ต้องผ่านก่อนส่งงาน |
| 9 | ตัวอย่างที่ทำงานได้ | `reference/api/Program.cs` (ส่วน `/purchase-requests`) | โค้ดอ้างอิงที่ทำตามเอกสารนี้ ใช้เทียบเมื่อเอกสารกำกวม |

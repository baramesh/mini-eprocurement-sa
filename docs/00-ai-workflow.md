# การทำงานกับ AI ในโปรเจกต์นี้

## 1. หลักการ

โปรเจกต์นี้ทำเพื่อแสดงวิธีทำงานของนักวิเคราะห์ระบบ (SA) ที่ใช้ AI เป็นเครื่องมือหลัก โดยยึดสามข้อ

1. **คนกำหนดโจทย์และขอบเขต AI ร่างและตรวจ** ผู้จัดทำเลือกธุรกิจ ชุดเอกสารที่ต้องมี และข้อจำกัด ส่วนค่าสมมติทางธุรกิจ (เช่น เกณฑ์วงเงิน) AI เสนอและระบุเป็นสมมติไว้ในเอกสาร เพื่อให้ผู้จัดทำตรวจรับ
2. **ให้สคริปต์ตรวจสิ่งที่ตรวจแบบแน่นอนได้** ความสอดคล้องข้ามเอกสารไม่ควรพึ่งการอ่านด้วยตาหรือความจำของ AI จึงเขียนตัวตรวจเป็นโค้ดและรันซ้ำได้
3. **ผลทุกอย่างสร้างซ้ำได้จาก source** เอกสารเขียนเป็น Markdown แล้วสร้าง PDF ด้วยสคริปต์ ไม่แก้ไฟล์ปลายทางด้วยมือ แก้ที่ต้นทางแล้วสร้างใหม่

เครื่องมือ AI ที่ใช้: Claude Code (Claude Sonnet 5.5) สำหรับร่าง แก้ข้ามไฟล์ รันสคริปต์ และดูภาพหน้าเอกสารที่สร้างจริงเพื่อหาข้อบกพร่องด้านการจัดหน้า ไฟล์คำสั่งประจำโปรเจกต์ของ agent เก็บไว้ในเครื่องผู้จัดทำ ไม่ได้อยู่ใน repository นี้ repository จึงแสดงผลงานและหลักฐาน ไม่ใช่ชุดตั้งค่าที่ใช้รันซ้ำ

## 2. ขั้นตอนและบทบาท

| ขั้น | ผู้จัดทำกำหนด | AI ทำ | ผลลัพธ์ | การตรวจ |
|---|---|---|---|---|
| 1. โจทย์ | ธุรกิจ (จัดซื้อจัดจ้างขนาดย่อ), ชุดเอกสาร SA ครบชุด, ไม่ใช้ข้อมูลหน่วยงานจริง, สร้างในเครื่องและยังไม่เผยแพร่ | ถามตัวเลือกขอบเขตให้ผู้จัดทำเลือก | ขอบเขตตามหัวข้อ 1.2 ของเอกสาร Requirements | ผู้จัดทำยืนยันก่อนเริ่ม |
| 2. Requirements | – (เกณฑ์วงเงินและสายอนุมัติเป็นสมมติที่ AI เสนอ รอผู้จัดทำตรวจรับ) | ร่าง FR 14 ข้อ, BR 12 ข้อ, NFR 6 ข้อ, ระบุสมมติฐานและสิ่งที่อยู่นอกขอบเขต | `docs/01-requirements.md` | ตัวตรวจอ่านรหัส FR/BR เป็นแหล่งอ้างอิงของเอกสารถัดไป |
| 3. กระบวนการและ Use Case | – | ร่างผังกระบวนการ, สถานะเอกสาร, UC 10 รายการ, ตัวอย่าง UC แบบละเอียด, sequence diagram | `docs/02-process-and-usecases.md` | ตัวตรวจ: ทุก UC อ้าง FR ที่มีจริง |
| 4. ข้อมูล | – (AI เลือก SQL Server T-SQL ให้ตรงกับเทคโนโลยีของตำแหน่งงานเป้าหมาย) | ออกแบบ 17 ตาราง, constraint, ดัชนี, ขั้นตอนออกเลขเอกสารแบบไม่ซ้ำ, บันทึกเหตุผลการออกแบบ | `sql/schema.sql`, `docs/03-data-model.md` | สคริปต์สร้างพจนานุกรมข้อมูล 106 คอลัมน์จากคอมเมนต์ใน SQL; รัน schema และชุดทดสอบฐานข้อมูลบน SQL Server 2022 จริง (สคริปต์ภายใน) |
| 5. API | – | เขียน OpenAPI 19 operation พร้อม `x-fr` และ `x-roles` ต่อ operation, รหัสข้อผิดพลาด 18 รหัส, กฎต่อ operation | `api/openapi.yaml`, `docs/04-api-spec.md` | ตัวตรวจ: `$ref` ทุกตัวหาเจอ, ทุก operation มี FR และบทบาทที่ถูกต้อง |
| 6. หน้าจอ | – | ร่างตารางหน้าจอ 10 หน้า, ผังนำทาง, รายละเอียดฟิลด์ของหน้าหลัก | `docs/05-screen-spec.md` | ตัวตรวจ: หน้าจออ้าง UC, FR, operationId ที่มีจริง |
| 7. ชุดทดสอบ | – | ออกแบบกรณีทดสอบ 51 กรณี ใช้การวิเคราะห์ค่าขอบกับเกณฑ์วงเงิน | `docs/06-test-cases.md` | ตัวตรวจ: ทุก FR และทุก operation มีกรณีทดสอบ; รหัสข้อผิดพลาดที่ระบุมีในตาราง |
| 8. สืบกลับ | – | เขียนตัวตรวจและตัวสร้างเมทริกซ์ | สคริปต์ตรวจความสอดคล้อง (ภายใน), `docs/07-traceability-matrix.md` | รันได้ผล 0 error; ตรวจรูปแบบไฟล์ที่สร้างว่าเป็นรุ่นล่าสุดด้วย `--check` |
| 9. สร้าง PDF | – | เขียนสคริปต์ md → pandoc → HTML → Chrome, สร้างสารบัญเลขหน้าสองรอบ, ดูภาพหน้าที่ได้แล้วแก้ | `output/*.pdf` | ดูภาพตัวอย่างหน้าที่เสี่ยง (ผัง, ตารางกว้าง) ผลที่พบอยู่ในหัวข้อ 3 |

## 3. ตัวอย่างสิ่งที่ตัวตรวจจับได้และสิ่งที่ AI แก้ระหว่างทาง

| เรื่อง | เกิดอะไรขึ้น | แก้อย่างไร |
|---|---|---|
| ช่องว่างในชุดทดสอบ | ตัวตรวจรายงานว่า operation `getPurchaseRequest` ไม่มีกรณีทดสอบเลย ทั้งที่ตาราง FR ดูครบ | เพิ่ม TC-50 (ดูรายละเอียดพร้อมสายอนุมัติ) และ TC-51 (ดูข้ามหน่วยงาน) |
| schema สร้างไม่ผ่านตอนรันจริง | รัน `schema.sql` บน SQL Server ครั้งแรกแล้ว filtered index `ux_quotation_active` ล้มเหลว เพราะ `sqlcmd` ตั้ง `QUOTED_IDENTIFIER` เป็น OFF โดยปริยาย ต่างจากการเชื่อมต่อของแอปที่เป็น ON ซึ่งการอ่านด้วยตาไม่เจอ | เพิ่ม `SET ANSI_NULLS ON; SET QUOTED_IDENTIFIER ON;` ที่หัวไฟล์ แล้วรันซ้ำบนฐานข้อมูลเปล่าจนผ่าน |
| บั๊กในตัวทดสอบที่ AI เขียนเอง | การทดสอบ TC-24 ล้มเหลวครั้งแรก เพราะอ้าง `quotation_id = 1` แต่ insert ที่ล้มเหลวก่อนหน้าใช้เลข identity ไปแล้ว | แก้ให้ UPDATE ตามคีย์ธุรกิจแทนเลข id; schema ไม่ได้ผิด |
| ตรวจว่าการทดสอบจับความผิดได้ | ผลผ่านอย่างเดียวพิสูจน์ไม่ได้ว่าตัวทดสอบมีประโยชน์ | เพิ่มตัวควบคุม: วิธี `MAX()+1` แบบไม่ล็อกรันภายใต้ภาระเดียวกัน ได้เลขซ้ำจำนวนมาก (ต่ำกว่า 1,000 เลขที่ไม่ซ้ำอย่างชัดเจน) ขณะที่ `usp_next_doc_no` ได้ 1,000 เลขไม่ซ้ำ |
| การออกแบบ endpoint อนุมัติ | ร่างแรกให้อนุมัติผลเลือกผู้ชนะผ่าน endpoint ของ PR โดยแยกด้วยฟิลด์ `target` ซึ่งปนความรับผิดชอบ | ระหว่างเขียนเอกสาร API เปลี่ยนเป็น endpoint กลาง `/approvals` ที่แยกชนิดงานด้วย `docType` แล้วแก้ sequence diagram ให้ตรง |
| ผังกระบวนการอ่านไม่ออก | ผังเดียวยาวถูกย่อจนตัวอักษรเล็ก | แยกเป็น 2 ผัง และเพิ่มขนาดฟอนต์ของ Mermaid |
| หัวข้อผังค้างท้ายหน้า | "ผังที่ 2" อยู่ท้ายหน้า ส่วนภาพไปหน้าถัดไป | เพิ่มกฎ CSS ให้ย่อหน้านำอยู่กับภาพเสมอ |
| รหัสกรณีทดสอบแตกบรรทัด | ในหน้าแนวนอน รหัสเช่น `TC-06` ถูกตัดเป็นสองบรรทัด | ตั้งคอลัมน์แรกของหน้าแนวนอนไม่ตัดบรรทัด |

## 4. สิ่งที่ตรวจแล้ว และสิ่งที่ยังไม่ได้ตรวจ

| ตรวจแล้ว (มีหลักฐานเป็นสคริปต์ ผลดิบ หรือภาพ) | ยังไม่ได้ตรวจ |
|---|---|
| ทุกรหัสที่อ้างกันระหว่างเอกสารมีอยู่จริง (สคริปต์ตรวจความสอดคล้องภายใน ได้ 0 error) | กรณีทดสอบระดับ API ยังไม่มีระบบจริงให้รัน |
| ทุก FR มี UC, API operation และกรณีทดสอบ (14 จาก 14); ทุก operation มีกรณีทดสอบ (19 จาก 19) | ประสิทธิภาพ (NFR-01) ยังไม่ได้วัดบนข้อมูล 100,000 PR |
| `sql/schema.sql` รันผ่านบน SQL Server 2022 จริง ได้ 17 ตาราง 106 คอลัมน์ ตรงกับพจนานุกรมข้อมูล | การออกเลขเอกสารทดสอบด้วย 20 การเชื่อมต่อบนเครื่องเดียว ไม่ใช่ภาระจากเครือข่ายจริง |
| ชุดทดสอบฐานข้อมูลผ่านทั้งหมด: constraint, สิทธิ์ของตาราง audit, การออกเลข 1,000 เลขไม่ซ้ำ ([`tests/db/RESULTS.md`](../tests/db/RESULTS.md)) | ยังไม่ได้ตรวจ OpenAPI ด้วยเครื่องมือตรวจมาตรฐานภายนอก ตัวตรวจในโปรเจกต์ตรวจเฉพาะโครงสร้างที่โปรเจกต์ใช้ |
| PDF สร้างจาก Markdown ด้วยสคริปต์ภายใน; ตรวจภาพหน้าสำคัญแล้ว | เกณฑ์วงเงินเป็นค่าสมมติ ไม่ได้เทียบกับระเบียบจัดซื้อจัดจ้างจริง |

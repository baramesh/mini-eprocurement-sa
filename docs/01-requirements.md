# ข้อกำหนดความต้องการ (Requirements)

## 1. ภาพรวมและขอบเขต

### 1.1 บริบทธุรกิจ

องค์กรสมมติแห่งหนึ่ง (พนักงาน ~300 คน ไม่ใช่หน่วยงานจริงใดๆ) ต้องการระบบจัดซื้อจัดจ้างขนาดย่อ ใช้แทนการขอซื้อด้วยกระดาษและอีเมล ปัญหาที่ต้องแก้:

- ใบขอซื้อหลายฉบับตามไม่ได้ว่าอยู่ขั้นไหนและรออนุมัติจากใคร
- การเทียบราคาผู้ขายทำในสเปรดชีตส่วนตัว ไม่มีหลักฐานว่าทำไมเลือกรายนั้น
- เลขที่เอกสารซ้ำหรือข้ามเมื่อหลายคนออกพร้อมกัน
- ตรวจย้อนหลังไม่ได้ว่าใครอนุมัติอะไรเมื่อไร

### 1.2 ขอบเขต

| อยู่ในขอบเขต | อยู่นอกขอบเขต |
|---|---|
| ใบขอซื้อ (PR), การอนุมัติหลายขั้น | งบประมาณและการกันงบ (Budget control) |
| ขอใบเสนอราคา (RFQ), บันทึกและเทียบราคา, เลือกผู้ชนะ | การประมูลอิเล็กทรอนิกส์ (e-Bidding) |
| ใบสั่งซื้อ (PO), ซื้อตรงวงเงินต่ำ | การตรวจรับใบแจ้งหนี้และจ่ายเงิน (Invoice matching, Payment) |
| รับของตาม PO (Goods Receipt) | การเชื่อมระบบบัญชี/ERP |
| ทะเบียนผู้ขาย, รายงานสรุป, audit trail | ผู้ขายล็อกอินเข้าระบบเอง (ในรุ่นนี้เจ้าหน้าที่จัดซื้อบันทึกแทน) |

### 1.3 ผู้เกี่ยวข้อง (Actor) และบทบาท

| รหัสบทบาท | ผู้ใช้ | สิ่งที่ทำได้ |
|---|---|---|
| `REQUESTER` | ผู้ขอซื้อ | สร้าง แก้ ส่ง PR ของตน |
| `DEPT_APPROVER` | หัวหน้าหน่วยงาน | อนุมัติ/ปฏิเสธ PR ของหน่วยงานตน |
| `PROCUREMENT` | เจ้าหน้าที่จัดซื้อ | สร้าง RFQ, บันทึกใบเสนอราคา, ออก PO, จัดการผู้ขาย |
| `PROCUREMENT_HEAD` | หัวหน้าจัดซื้อ | อนุมัติ PR และผลเลือกผู้ชนะ |
| `COMMITTEE` | คณะกรรมการ | อนุมัติ PR และผลเลือกผู้ชนะวงเงินสูง |
| `RECEIVER` | ผู้รับของ | บันทึกการรับของ |
| `ADMIN` | ผู้ดูแลระบบ | จัดการผู้ใช้และดู audit trail |

## 2. ข้อกำหนดเชิงหน้าที่ (Functional Requirements)

| รหัส | ข้อกำหนด | ลำดับ |
|---|---|---|
| FR-01 | ผู้ขอซื้อสร้างและแก้ไข PR สถานะ draft ได้ โดยระบุหัวข้อ เหตุผล วันที่ต้องการ และรายการสินค้า/บริการ | Must |
| FR-02 | ค้นหาและดูรายการ PR ตามสถานะ ช่วงวันที่ และผู้ขอซื้อ ผู้ขอซื้อเห็นเฉพาะของตน ผู้อนุมัติเห็นของหน่วยงานตน | Must |
| FR-03 | ผู้ขอซื้อส่ง PR เพื่ออนุมัติ ระบบตรวจความครบถ้วนและคำนวณวงเงินรวม | Must |
| FR-04 | ผู้อนุมัติอนุมัติหรือปฏิเสธ PR ตามสายอนุมัติที่ขึ้นกับวงเงินรวม (BR-03) การปฏิเสธต้องระบุเหตุผล | Must |
| FR-05 | เจ้าหน้าที่จัดซื้อสร้าง RFQ จาก PR ที่อนุมัติแล้วและเชิญผู้ขายอย่างน้อย 3 ราย เมื่อวงเงินเกินเกณฑ์ซื้อตรง | Must |
| FR-06 | เจ้าหน้าที่จัดซื้อบันทึกใบเสนอราคาของผู้ขายที่ได้รับเชิญ ภายในกำหนด RFQ | Must |
| FR-07 | ดูตารางเปรียบเทียบราคาของทุกรายต่อรายการ พร้อมราคารวม ระยะเวลาส่งมอบ และรายที่ราคาต่ำสุด | Must |
| FR-08 | เลือกผู้ชนะพร้อมเหตุผล ถ้าไม่ใช่ราคาต่ำสุดต้องมีเหตุผลอย่างน้อย 20 ตัวอักษร แล้วส่งอนุมัติผลตามวงเงิน | Must |
| FR-09 | ออก PO จากผลที่อนุมัติ หรือออก PO ซื้อตรงเมื่อวงเงิน PR ไม่เกินเกณฑ์ซื้อตรง | Must |
| FR-10 | บันทึกการรับของตาม PO ทั้งครบและบางส่วน ปฏิเสธจำนวนที่เกินยอดคงเหลือ | Must |
| FR-11 | จัดการทะเบียนผู้ขาย: เพิ่ม แก้ ระงับ ตรวจเลขผู้เสียภาษี 13 หลักไม่ซ้ำ | Should |
| FR-12 | รายงานสรุปการจัดซื้อตามช่วงเวลา หน่วยงาน ผู้ขาย: จำนวนเอกสาร มูลค่า และส่วนต่างจากราคากลางที่ประมาณ | Should |
| FR-13 | บันทึก audit trail ทุกการเปลี่ยนสถานะและการตัดสินใจ ห้ามแก้หรือลบ | Must |
| FR-14 | ออกเลขเอกสาร PR/RFQ/PO/GR อัตโนมัติรูปแบบ `<ชนิด>-<ปี ค.ศ.>-<ลำดับ 5 หลัก>` ไม่ซ้ำแม้ออกพร้อมกัน | Must |

## 3. กฎธุรกิจ (Business Rules)

| รหัส | กฎ | ใช้กับ |
|---|---|---|
| BR-01 | PR วงเงินรวม **ไม่เกิน 5,000 บาท** ซื้อตรงได้ ไม่ต้องทำ RFQ | FR-05, FR-09 |
| BR-02 | PR วงเงินรวม **เกิน 5,000 บาท** ต้องทำ RFQ เชิญผู้ขายอย่างน้อย 3 ราย และมีใบเสนอราคาอย่างน้อย 2 ราย ก่อนเลือกผู้ชนะ | FR-05, FR-08 |
| BR-03 | สายอนุมัติ PR ตามวงเงินรวม: ไม่เกิน 20,000 = `DEPT_APPROVER`; 20,001–200,000 = `DEPT_APPROVER` แล้ว `PROCUREMENT_HEAD`; เกิน 200,000 = ทั้งสองแล้ว `COMMITTEE` อนุมัติตามลำดับ | FR-04 |
| BR-04 | ผู้ขอซื้อห้ามอนุมัติ PR ของตนเอง แม้มีบทบาทผู้อนุมัติ (แยกหน้าที่) | FR-04, FR-08 |
| BR-05 | ผลเลือกผู้ชนะวงเงินเกิน 200,000 ต้องได้รับอนุมัติจาก `COMMITTEE` ที่เหลืออนุมัติโดย `PROCUREMENT_HEAD` | FR-08 |
| BR-06 | เลือกผู้ขายที่ไม่ใช่ราคาต่ำสุดได้เมื่อมีเหตุผลอย่างน้อย 20 ตัวอักษร | FR-08 |
| BR-07 | ใบเสนอราคารับได้เฉพาะผู้ขายที่ได้รับเชิญและก่อนเวลาปิด RFQ | FR-06 |
| BR-08 | ผู้ขายหนึ่งรายมีใบเสนอราคาที่ใช้งานได้ 1 ฉบับต่อ RFQ การบันทึกซ้ำแทนที่ฉบับเดิมและเก็บประวัติ | FR-06 |
| BR-09 | PO ซื้อตรงต้องไม่เกินวงเงิน PR ที่อนุมัติ; PO จากผลประกวดใช้ราคาตามใบเสนอราคาที่ชนะ | FR-09 |
| BR-10 | จำนวนรับของสะสมต่อรายการห้ามเกินจำนวนสั่ง; จำนวนที่ปฏิเสธไม่นับเป็นรับ | FR-10 |
| BR-11 | ผู้ขายสถานะระงับ (`SUSPENDED`) เชิญหรือออก PO ไม่ได้ | FR-05, FR-09, FR-11 |
| BR-12 | เอกสารที่อนุมัติแล้วแก้ไขรายการไม่ได้ ต้องปฏิเสธกลับเป็น draft หรือยกเลิกแล้วสร้างใหม่ | FR-01, FR-04 |

## 4. ข้อกำหนดที่ไม่ใช่เชิงหน้าที่ (Non-functional Requirements)

| รหัส | หัวข้อ | เกณฑ์ที่วัดได้ |
|---|---|---|
| NFR-01 | ประสิทธิภาพรายการ | หน้ารายการ PR (50 แถวต่อหน้า) ตอบ p95 ไม่เกิน 1 วินาที เมื่อมี PR 100,000 รายการ |
| NFR-02 | ความสมบูรณ์ audit trail | ตาราง audit รับเฉพาะ INSERT; บัญชีที่แอปใช้ไม่มีสิทธิ์ UPDATE/DELETE |
| NFR-03 | ความปลอดภัย | ทุก endpoint ตรวจสิทธิ์ตามบทบาท; ข้อมูลข้ามหน่วยงานเข้าถึงไม่ได้ตามกฎ FR-02; ป้องกัน OWASP Top 10 ในส่วนที่เกี่ยวข้อง |
| NFR-04 | ความถูกต้องของเลขเอกสาร | ออกเลข 1,000 เอกสารพร้อมกัน 20 เธรด ไม่ซ้ำและไม่ข้าม |
| NFR-05 | การเรียกซ้ำปลอดภัย | คำสั่งเปลี่ยนสถานะรองรับ `Idempotency-Key` ส่งซ้ำไม่ทำงานซ้ำ |
| NFR-06 | การใช้งานภาษา | ข้อความหน้าจอและข้อความผิดพลาดเป็นภาษาไทย ฟิลด์วันที่แสดงเป็น พ.ศ. จัดเก็บเป็น UTC |

## 5. สมมติฐานและข้อจำกัด

- เกณฑ์วงเงิน (5,000 / 20,000 / 200,000 บาท) เป็นค่าสมมติของโจทย์นี้เพื่อให้มีกรณีขอบเขตสำหรับออกแบบและทดสอบ **ไม่ได้อ้างอิงระเบียบจัดซื้อจัดจ้างของหน่วยงานใด** และต้องเก็บเป็นค่าตั้งค่าในระบบจริง
- ราคาทั้งหมดเป็นบาท ไม่รวมภาษีมูลค่าเพิ่ม (VAT) ในรุ่นนี้
- ผู้ใช้ยืนยันตัวตนผ่านระบบกลางขององค์กร (SSO) นอกขอบเขตเอกสารนี้ API รับข้อมูลผู้ใช้จาก token เท่านั้น

# ข้อกำหนด REST API

สัญญา API ที่เครื่องมืออ่านได้อยู่ที่ `api/openapi.yaml` (OpenAPI 3.0.3) เอกสารนี้อธิบายหลักการและกฎที่ schema บอกไม่ได้ รายการ endpoint ครบทุกรายการอยู่ในเอกสาร 04a (สร้างอัตโนมัติจาก OpenAPI)

## 1. หลักการทั่วไป

| หัวข้อ | ข้อกำหนด |
|---|---|
| Base URL และเวอร์ชัน | `/api/v1` เปลี่ยนที่ทำให้ client เดิมพังต้องขึ้น `/v2` |
| รูปแบบข้อมูล | JSON, UTF-8; วันที่เวลาเป็น ISO 8601 UTC; เงินเป็นตัวเลขทศนิยม 2 ตำแหน่ง หน่วยบาท |
| การยืนยันตัวตน | `Authorization: Bearer <JWT>` ออกโดย SSO; API อ่านรหัสผู้ใช้และบทบาทจาก claim ไม่รับจาก body |
| การตรวจสิทธิ์ | ตรวจบทบาทตาม `x-roles` ของแต่ละ operation แล้วตรวจขอบเขตข้อมูล (หน่วยงาน, เจ้าของเอกสาร) ใน service; ไม่ผ่านตอบ 403 `ERR-AUTH-002` |
| การเรียกซ้ำ | คำสั่งที่เปลี่ยนสถานะรับ `Idempotency-Key` (UUID); เก็บผลไว้ 24 ชั่วโมง; ส่งซ้ำด้วย payload เดิมได้ผลเดิม; payload ต่างจากเดิมตอบ 422 `ERR-IDEM-001` |
| การแก้ไขซ้อน | `PUT` ใบขอซื้อต้องมี `If-Match` เป็น `rowVersion`; ไม่ตรงตอบ 409 `ERR-CONC-001` |
| Pagination | keyset: ส่ง `cursor` ที่ได้จาก `nextCursor`; `limit` 1–100 (ค่าเริ่มต้น 50) |
| ภาษาข้อความ | `message` เป็นภาษาไทย; `code` เป็นรหัสคงที่ให้ client แปลงเอง |

## 2. รูปแบบข้อผิดพลาด

```json
{
  "code": "ERR-RFQ-001",
  "message": "ต้องเชิญผู้ขายอย่างน้อย 3 ราย",
  "details": [{ "field": "vendorIds", "issue": "minItems: 3" }]
}
```

### 2.1 รหัสข้อผิดพลาด

| รหัส | HTTP | ความหมาย | กฎที่เกี่ยว |
|---|---|---|---|
| ERR-VAL-001 | 422 | ข้อมูลไม่ผ่านการตรวจ (ฟิลด์ขาด รูปแบบผิด ช่วงค่าผิด) | – |
| ERR-AUTH-001 | 401 | ไม่มี token หรือ token หมดอายุ | – |
| ERR-AUTH-002 | 403 | บทบาทหรือขอบเขตข้อมูลไม่อนุญาต | NFR-03 |
| ERR-SOD-001 | 403 | ผู้ขอซื้ออนุมัติ PR ของตนเอง | BR-04 |
| ERR-STATE-001 | 409 | สถานะเอกสารไม่รองรับการกระทำนี้ หรือขั้นอนุมัตินี้ตัดสินแล้ว | BR-12 |
| ERR-STATE-002 | 409 | PR ยังไม่อนุมัติ จึงสร้าง RFQ/PO ไม่ได้ | FR-05, FR-09 |
| ERR-CONC-001 | 409 | ข้อมูลถูกแก้โดยผู้อื่นแล้ว (`If-Match` ไม่ตรง) | – |
| ERR-IDEM-001 | 422 | `Idempotency-Key` เดิมแต่ payload ต่างกัน | NFR-05 |
| ERR-RFQ-001 | 422 | เชิญผู้ขายน้อยกว่า 3 ราย | BR-02 |
| ERR-RFQ-002 | 422 | ผู้ขายไม่ได้รับเชิญใน RFQ นี้ | BR-07 |
| ERR-RFQ-003 | 409 | RFQ ปิดรับแล้ว | BR-07 |
| ERR-RFQ-004 | 422 | เลือกรายที่ไม่ใช่ราคาต่ำสุดแต่เหตุผลไม่ถึง 20 ตัวอักษร | BR-06 |
| ERR-RFQ-005 | 422 | มีใบเสนอราคาน้อยกว่า 2 ราย ยังเลือกผู้ชนะไม่ได้ | BR-02 |
| ERR-RFQ-006 | 422 | PR วงเงินไม่เกิน 5,000 บาท ซื้อตรงได้ ไม่ต้องสร้าง RFQ | BR-01 |
| ERR-PO-001 | 422 | ซื้อตรงเกินวงเงินที่กำหนด หรือมูลค่า PO เกินวงเงิน PR | BR-01, BR-09 |
| ERR-VND-002 | 422 | ผู้ขายถูกระงับ ใช้เชิญหรือออก PO ไม่ได้ | BR-11 |
| ERR-VND-001 | 409 | เลขประจำตัวผู้เสียภาษีซ้ำ | FR-11 |
| ERR-GR-001 | 422 | จำนวนรับสะสมเกินจำนวนสั่ง | BR-10 |

## 3. กฎรายละเอียดของ operation ที่ซับซ้อน

| operationId | ตรวจอะไรบ้าง (ตามลำดับ) | ผลสำเร็จ |
|---|---|---|
| `submitPurchaseRequest` | สถานะต้องเป็น `DRAFT` (`ERR-STATE-001`); มีรายการอย่างน้อย 1; คำนวณ `totalEstimated`; สร้างแถว `approval` ตาม BR-03; บันทึก `row_version`; audit `SUBMIT` | `SUBMITTED` พร้อมสายอนุมัติ |
| `decideApproval` | ขั้นปัจจุบันตรงบทบาทผู้เรียก; ผู้เรียกไม่ใช่ผู้ขอซื้อ/ผู้เสนอผล (`ERR-SOD-001`); ขั้นยัง `PENDING` (`ERR-STATE-001`); ปฏิเสธต้องมี `comment`; ถ้าอนุมัติและเป็นขั้นสุดท้าย เปลี่ยนสถานะเอกสาร | อนุมัติขั้นสุดท้าย: PR เป็น `APPROVED` หรือ RFQ เป็น `AWARDED`; ปฏิเสธ: PR กลับ `DRAFT`, RFQ กลับ `OPEN` |
| `createRfq` | PR สถานะ `APPROVED` (`ERR-STATE-002`); วงเงินเกิน 5,000 (`ERR-RFQ-006`); `vendorIds` ≥ 3 (`ERR-RFQ-001`); ผู้ขายทุกรายสถานะ `ACTIVE` (`ERR-VND-002`); ออกเลข RFQ; PR เป็น `IN_SOURCING` | `201` |
| `recordQuotation` | RFQ ยัง `OPEN` และก่อน `dueAt` (`ERR-RFQ-003`); ผู้ขายได้รับเชิญ (`ERR-RFQ-002`); ครอบคลุมทุกรายการของ PR; ฉบับเดิมเป็น `is_active = 0` | `201` |
| `awardRfq` | มีใบเสนอราคา ≥ 2 ราย (`ERR-RFQ-005`); ถ้าไม่ใช่ราคาต่ำสุดต้องมีเหตุผล ≥ 20 ตัวอักษร (`ERR-RFQ-004`); สร้างสายอนุมัติผลตาม BR-05; RFQ เป็น `AWARD_PENDING` | `202` |
| `createPurchaseOrder` | โหมดซื้อตรง: PR `APPROVED`, วงเงินไม่เกิน 5,000, ผู้ขาย `ACTIVE`; โหมดผลประกวด: RFQ `AWARDED` ใช้ราคาจากใบเสนอราคาที่ชนะ; มูลค่าไม่เกินวงเงิน PR (`ERR-PO-001`); PR เป็น `ORDERED` | `201` สถานะ `DRAFT` |
| `recordGoodsReceipt` | PO สถานะ `ISSUED` หรือ `PARTIALLY_RECEIVED`; รับสะสม ≤ จำนวนสั่งต่อรายการ (`ERR-GR-001`); คำนวณสถานะ PO ใหม่; ถ้ารับครบทุกรายการ PR เป็น `CLOSED` | `201` |

## 4. การเปลี่ยนแปลงที่ทำให้ client พัง (Breaking changes)

- **ถือเป็น breaking:** ลบหรือเปลี่ยนชื่อฟิลด์, เปลี่ยนชนิดข้อมูล, เพิ่มค่า enum ในฟิลด์ที่ client ใช้ switch, เปลี่ยนความหมายของ error code เดิม, เพิ่มฟิลด์บังคับใน request
- **ไม่ถือเป็น breaking:** เพิ่มฟิลด์ใน response, เพิ่ม endpoint, เพิ่ม error code ใหม่
